# Företag v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A company space (`orgs.kind = 'foretag'`) where the database lets each member see only the meetings and tasks the company tree allows them to see, with suggest-only tasks, customer pages and no billing.

**Architecture:**
- **Database:** one additive migration (0050) adds a tree of `groups`, a node per person (`people.group_id`), a group and a Privat möte flag per meeting, and stored attendees. It also adds one security-definer predicate, `foretag_can_see(user, …)`, that `meetings_select` and `is_meeting_member()` delegate to. Every table under a meeting therefore follows with no other policy edits. The predicate returns `is_org_member` for every non-Företag row, so föreningar and Privat keep today's answers.
- **App code:** each service-role path (Doc shares, summary mail, carried tasks, joining) asks the same SQL predicate through `foretag_viewer_ids(meeting)`, so there is one source of truth.
- **UI:** the Företag UI is a separate view behind the existing `/orgs/[id]` route (an early branch, like Privat's redirect). The förening page code is not edited.

**Tech Stack:** Next.js 16 (app router, server actions), Supabase Postgres + RLS, next-intl (sv/en JSON under `lib/i18n/messages`), vitest (unit + `tests/db` against the local stack in CI), Playwright e2e with fakes.

**Spec:** `docs/superpowers/specs/2026-11-27-foretag-v1-design.md`

## Global Constraints

- Migrations are additive and backward compatible with the deployed v1 code. The next number is `0050`. Every new column is nullable or defaulted, and no existing column changes meaning for a förening or Privat row.
- The visibility rule from the spec, verbatim, is enforced by RLS:
  - You see the meetings of your own group, plus every meeting of any group deeper in the tree than your own level.
  - Company admins see everything. A Hela företaget meeting is seen by every member.
  - You always see your own tasks.
  - A Privat möte is seen only by its attendees and admins.
  - The starter and the attendees always see the meeting.
- Föreningar behave exactly as today. The existing tests run unchanged, and a new DB test pins förening visibility.
- Företag tasks are suggest-only: `require_task_fields = false` at creation, `taskMode()` already returns `suggest`, there is no Avsluta dialog and the Doc carries no placeholders.
- There is no billing. All copy is in sv and en (`lib/i18n/no-swedish-literals.test.ts` must pass). The UI follows the house design (components/ui, design-guard test): no layout shift, labelled states, and transitions from the existing tokens.
- Creating a Företag is allowed only for `FORETAG_CREATOR_EMAILS`, which falls back to `ADMIN_EMAILS` and then `ALARM_EMAIL` through `isAdminEmail`. That is the DPA gate.
- One live meeting per company at a time. This is the existing org guard 0027, kept for v1.
- Never touch the prod DB and never push main.

## Review Focus

1. **A member re-links a person row to themselves to inherit its node.** `people_update` lets any member set `member_user_id` today, so in a Företag every people write must be admin-only. Test: as a member, updating `member_user_id` on Ledning's person row changes no row.
2. **A member writes their own placement.** `people.group_id`, `meetings.group_id/private` and `meeting_attendees` get no client grants. Test: as a member, writing `people.group_id` fails (permission denied).
3. **An account linked to no person.** Treat it as unplaced (fail closed): it sees only Hela företaget, started or attended meetings and its own tasks. Test: an unplaced member sees no group meeting.
4. **Moving a group under its own descendant**, or moving a group at all. A cycle is refused, and moving a subtree recomputes the depths. Test: `set_group` to a descendant parent raises, and after a move the child depths equal the parent's depth + 1.
5. **A member who cannot see a Doc is in the share list or the mail list.** Test: unit tests for the viewer filter in the start and summary paths, with a Privat möte excluding a non-attending head.

### Task 2: Pure Företag logic

**Files:**
- Create: `lib/foretag/customers.ts`, `lib/foretag/tree.ts`, `lib/foretag/audience.ts`, each with a `.test.ts`

**Interfaces:**
- `customerDomain(emails: string[], ownDomains: string[]): string | null`. The free-mail list is `FREE_MAIL`. With several external domains the one with the most attendees wins, and a tie goes to the first seen.
- `customerName(domain: string): string`. "acme.se" → "Acme", "nordic-tools.com" → "Nordic Tools", "mail.acme.co.uk" → "Acme".
- `ownDomains(memberEmails: string[]): string[]`.
- `treeRows(groups: GroupRow[]): { group: GroupRow; depth: number }[]`, in depth-first order by position then name. Archived groups are excluded.
- `audienceUserIds(input: { groupId: string | null; people: { member_user_id: string | null; group_id: string | null }[]; memberIds: string[]; attendeeIds: string[]; viewerIds: string[] }): string[]`. It returns the meeting's group (or every member when the group is null) plus the attendees, ∩ viewers.

- [ ] Step 1: Tests with the spec's examples, including gmail-only → null, own domain → null, and the two-domain majority.
- [ ] Step 2: Run them and see them fail. Step 3: implement. Step 4: they pass. Step 5: commit `feat(foretag): customers, tree, audience`.
